# 1.2.7：把候选图搜索与现场验路分开

1.2.6实测仍未通过。上方几次完整路线耗时583～885毫秒，下方多次整轮30秒取消，用户也报告久等、经常没有路线。这不能算楼梯修复完成。1.2.7是算法修复候选，现场正确率和延迟仍待验证。

## 已证明的原因

原始作者点中，楼梯有一处222.049厘米的采样间隙，旧候选连边上限只有210厘米。两端分别是`[-63339.1,219760.6,-12205.5]`与`[-63519.8,219797.7,-12081.9]`。即使所有碰撞检查都返回可走，旧图也无法由下方起点连到塔顶；搜索会在低层点内不断扩展。单纯优化A*堆或改为异步不能生成这条缺失的边。

旧版还在扩展每个候选邻点时立即调用实际步进检查。捕获的失败预检有1015次调用，多数通过但仍耗尽执行预算；分帧等待进一步放大了墙钟耗时。原始日志、1366运行文件完整安装核验及摘要见`authoring/field-retest-1.2.6.json`。

## 新实现

新增`PBZRouteHintWalk.js`，由原来的作者点预检入口调用，普通局部网格和其他回退保留：

1. 使用同一批546个作者点、起点和同层接近点，先只做有限三维图A*。候选跨度最多3.5米，楼层高度独立保留，垂直变化还经过粗筛；跨度只生成候选，不认证通行。
2. 对选出的路线才调用原有`world.step`。它继续沿途以原来的细步长检查实际脚下、可走坡度、跨步、角色身体、楼层和门锁；没有把3.5米变成可跳过的空档。
3. 一条边失败，只在本次任务剔除该有向边，再从候选图重算。已通过的边可在同一任务、相同实际起点下复用；新请求没有任何物理有效性缓存。候选路线未全部通过，不当成完整导航显示。
4. 每次候选图搜索最多768节点；整次预检最多64次物理连接检查、16次候选尝试，仍受200毫秒执行预算与整轮30秒墙钟上限约束。图搜索、物理预算、无候选图通路分别记录，不将预算失败称为不可达。
5. 原生/离线网格、动作、局部走路和回退继续参与；目标XYZ、存档、游戏设置及作者数据不变。没有新增固定课程、运行时轨迹学习、持续扫描或服务器。

这是借鉴Lazy PRM“候选先求路、按路认证、删除失败边”的结构，不是完整随机采样规划器，也不继承其理论完备性或全局最优性。UE官方、开源注入Mod、Recast/Detour、OMPL与工程插件的适用边界见[NAVIGATION-ARCHITECTURE-RESEARCH-20261114.md](NAVIGATION-ARCHITECTURE-RESEARCH-20261114.md)。本轮没有移植其他项目代码或改变许可。
