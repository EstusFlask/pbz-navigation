## 优先目标与现状

优先解决穿墙、明显绕远、上下层误接和特殊动作断路。现有全地图解锁存档可以先承担道路、楼层、动作及大部分目标接近测试；已收集物品不妨碍测道路，但无法验证真实拾取后的目标清除与部分机关未解锁状态。

- 主规划器已经调用 UE 原生 `NavigationSystemV1.FindPathToLocationSynchronously`，检查 `IsValid`、`IsPartial` 和起终点偏差；不能把“接入原生 NavMesh”描述成尚未实现的全新方案。见 `PBZQuestRoute.js` 的 `nativeWalk`。
- 现有系统同时使用离线路网、局部行走搜索、动作连接、当前碰撞与锁状态检查。首先需要查明错误出在数据、状态、验证还是绘制阶段，再决定更换或改造哪一层。
- `authoring/roadbook-course-audit.json` 的140条工作连接分为：2条轨迹参考、86条需当前场景检查的候选、49条缺连续几何、1条缺身份、1条缺跨world入口绑定、1条缺端点。它们不是全图通过率；候选与历史轨迹也不等于本版实测。
- 正式版已撤回玩家通路学习。建议增加独立、默认关闭的开发采集模式，数据供作者离线分析与审核，不自动改变普通玩家的正式路网。

## 先做的三个开发工具

1. **失败案例导出**：一次规划使用固定case ID，关联选择目标、候选、第一次拒绝、修补、整体验证和实际绘制终点。保留原始数值，减少靠日志截图猜测。
2. **短段采集与事件标记**：手动开始/结束，只记录本次脚点、移动模式、动作入口/出口、附近相关机关与世界切换。传送、死亡、重载和长采样缺口必须切段，不用直线填补。
3. **强制步行与原生导航探针**：全解锁档测试铃铛时关闭本次规划的铃铛中转；分别记录原生查询结果及现有规划器结果。当前公开配置没有强制步行开关，不要求用户寻找不存在的菜单。

采集模式应有明显状态、大小上限与结束后一次导出；查询和磁盘写入需有预算。游戏中不执行全图高频Actor扫描。仍只交付导航自有文件，不替换收集Mod。

## 用户需要配合的操作

每个案例只测一小段：

1. 在明确地标或铃铛旁出发，选定固定目标；记录希望“全程步行”还是允许传送。
2. 按导航前进，到第一次明显错误处停下并标记：穿墙、绕远、错层、漏动作或有路无导航。不要先换目标。
3. 从附近安全位置按正常游戏方式手动走通正确道路。动作前和落地后各稍停，方便对齐事件；能安全返回时再单独记录返程。
4. 到终点结束本次采集；简述“哪里错、正常怎么走”。一段短视频有助于辨认动作与画面，但连续XYZ与引擎状态应由工具自动记录。
5. 修复后回到原起点直接选目标再测；分别检查首次进入区域与刚走过的区域，避免把已加载场景带来的偶然成功当作修复。

不要求用户手抄坐标、识别Actor类名，或为了采样重复危险跳落。单向动作未实测返程时仅保留已观察方向。

## 自动采集的数据

| 数据 | 最少内容 | 用途 |
| --- | --- | --- |
| 案例身份 | 游戏/Mod版本、case ID、时间、起终点ID、world/区域、路线提供者、是否禁用中转 | 对齐复现、区分跨场景与同名目标 |
| 玩家实际移动 | 脚点XYZ、胶囊尺寸、MovementMode/CustomMovementMode、实际CurrentFloor、动作开始/结束 | 核对楼层、支撑、落脚与动画锚点 |
| 导航判定 | 原始候选、动作类型、每次修补前后折线、首次拒绝原因和边、最终显示线终点 | 定位规划、验证、简化或绘制哪层产生偏差 |
| 物理命中 | 扫线/胶囊起终点、profile、simple/complex、命中Actor/组件、法线、穿透状态 | 区分真实墙体、查询偏差与脚点高度错误 |
| 原生导航 | 可取得的NavData/agent信息、端点投影及偏移、完整/部分/无路径、点列、调用耗时 | 判断原生数据覆盖、楼层投影与接入价值 |
| 动作与条件 | Actor稳定身份、类、入口/出口/样条、方向、交互条件、门/梯/武装状态 | 补连续动作链，避免仅凭邻近坐标误连 |
| 加载与跳变 | 相关Actor驻留情况、可取得的流送状态、world变化、传送/死亡/重载事件 | 未加载不等于无障碍，跳变不等于连续道路 |

原生接口或底层路径标记不能通过反射取得时，先记录“不可取得”；不编造值，也不以此为由立即做未知ABI的原生调用。原生调用是同步的，探针不能每帧重复运行。

## 首批案例顺序

先收集5—10个能重复复现的短案例，每修复一类就复测并沉淀回归，不先要求玩家跑完52条缺失连接。新增采集优先`worksheet-014`等未编制连接；下面列出的已有手工路线用于后续回归校准，不作为首个新增路线采集任务。

1. **最后的挽回之地附近的普通道路**：现有游戏日志已出现局部连接通过、整体验证随后因不可走地面而拒绝的现象。对比这两阶段的脚点、投影、采样与状态。日志不足以证明具体碰撞或验证规则有错，需要现场对照。
2. **幻鬼酒馆附近的障碍与侧路**：已有真实坐标fixture，但测试碰撞是模拟的。现场分别核对直线是否阻挡、侧路是否确实可走。
3. **大廊桥→陆家村小张藏身处**：保留山洞内连续攀爬与钩索；验证每个入口、落脚和动作之间的普通步行连接。
4. **乱葬岗→墨玑子衣冠冢**：核对下降、绕坡上行、上下层接入与终点到达。
5. **一组上下层近距离目标与一组单向动作**：同一平面位置分别在上层/下层出发；下降和返程分开处理。可选已知物品坐标作测试目标，但不能因此宣称真实拾取流程已验证。

以上地点若当前不可访问，可替换为同类型、玩家能演示正确走法的短路段。路线准确性稳定后，再按 `MOVEMENT-COVERAGE.md` 补缺失连接与跨world/船行通道。

## 验收方式

- **穿墙**：当前碰撞明确阻挡之后不继续显示已确认可行的场景线；区分角色能通过但抬高蓝线碰墙的显示问题。
- **错层**：起点与目标保持明确楼层；在目标正上方/下方不误报到达，不吸附到隔层路段。
- **特殊动作**：提示正确入口和落脚，动作中保留目标，落地后无需重新选目标即可继续；不因记录过一个方向就生成反向。
- **绕路**：将计算出的可执行路线与本次人工走通路线比较，检查漏掉的开放通道和成本规则；人工路线只是已知可行参照，不是全局最短证明。传送、步行和动作时间应分开比较。
- **可重复性**：从原起点首次选目标即可复现修复；记录引擎实测、离线真实数据回放与模拟测试三种证据的各自范围。

## 存档需求

现在先使用现有全解锁档。物品坐标可以来自已有目录，并可在导航自有开发目标中引用；已收集后的场景不适合证明拾取交互、目标消失、一次性可破坏物或未开启状态。

第二阶段再补一个保留较多物品与未开启门梯的中期存档，用于“开启前→开启后”“拾取前→拾取后”“缺能力→具备能力”。这时先明确要复现的状态，再寻找同平台、同游戏版本的存档；不需要为采道路立即更换现有存档。
